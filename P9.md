## 1. Project Objectives Summary

The primary objective of this project is to develop and evaluate an **Entropy-Guided Hierarchical Load Balancing Framework** for heterogeneous HPC clusters. Specifically, the framework aims to:

1. **Multi-Level Topology Awareness:** Maintain an aggregated, multi-level hierarchy reflecting physical cluster topology (Cluster $\to$ Rack $\to$ Compute Node).
2. **Multi-Dimensional Resource Adaptation:** Balance multi-resource demands simultaneously (CPU, memory, network I/O, disk I/O) using workload-specific composite scoring.
3. **Entropy-Based Stability Classification:** Quantify runtime load volatility and entropy ($H$) to distinguish between stable nodes and volatile/bursty nodes.
4. **Logarithmic Scheduling Efficiency:** Achieve scalable $O(\log N)$ query and update complexity (overcoming flat list $O(N)$ bottlenecks) for clusters with thousands of nodes.
5. **System Performance Optimization:** Substantially reduce makespan (10–25%), job wait times (15–30%), and node load variance (30–50%) compared to traditional static and dynamic baselines.

## 2. Problem Statement

High-performance computing (HPC) clusters execute large-scale parallel jobs across hundreds or thousands of compute nodes. Efficient **load balancing** is critical to minimize job completion time (makespan), reduce resource idle time, and improve overall system throughput. 

However, modern HPC workloads are increasingly **heterogeneous** (varying CPU, memory, I/O, and GPU requirements) and **dynamic** (jobs arrive over time, node performance varies due to hardware aging, thermal throttling, network congestion, or interference from co-located jobs).

### Limitations of Existing Approaches:
- **Static partitioning** (e.g., round-robin, block/cyclic distribution): Ignores runtime load variations and workload heterogeneity.
- **Simple dynamic heuristics** (e.g., assign to least-loaded node): Consider only instantaneous load (e.g., CPU utilization) but ignore:
  - **Load variability:** Some nodes exhibit stable performance, while others fluctuate significantly.
  - **Multi-dimensional resource requirements:** CPU-bound vs. memory-bound vs. I/O-bound jobs.
- **Centralized schedulers:** Become severe bottlenecks at large scale, while **fully decentralized approaches** lack global coordination and lead to suboptimal decisions.
- **Flat data structures** (e.g., simple lists or arrays for load tracking): Require $O(N)$ time to find the least-loaded node, which is inefficient for clusters with thousands of nodes.

### Framework Requirements:
There is an urgent need for a **hierarchical load-balancing framework** that:
1. Maintains a **multi-level view** of cluster load (Cluster $\to$ Rack $\to$ Node).
2. Adapts to **workload heterogeneity** by considering multiple resource dimensions (CPU, memory, network, disk I/O).
3. Accounts for **load variability (entropy)** to distinguish between stable and unstable nodes.
4. Supports **efficient query and update operations** ($O(\log N)$ time) for job assignment and load monitoring.
5. Reduces **load imbalance** (variance in node utilization) and **job makespan** compared to existing methods.

## 3. Novelty Justification

The proposed work introduces several key scientific and algorithmic novelties:

### 3.1. Entropy-Guided Node Grouping
Unlike existing methods that group nodes by simple load averages, we propose grouping nodes based on **load entropy** (variability in CPU, memory, network usage over time):
- **Low-Entropy Nodes:** Exhibit stable, predictable performance. Suitable for long-running, predictable HPC jobs.
- **High-Entropy Nodes:** Exhibit variable performance. Suitable for short, bursty jobs or jobs with flexible deadlines.
- **Job-Node Matching:** Enables intelligent matching based on job characteristics (predictable vs. bursty).

### 3.2. Hierarchical Load Tracking
We design a **multi-level tree structure** that mirrors the physical topology of HPC clusters (Cluster $\to$ Rack $\to$ Node). Each tree node aggregates load metrics from its children, enabling:
- **Coarse-to-fine scheduling:** First select the best rack, then the best node within that rack.
- **Scalable queries:** $O(\log N)$ time to find the least-loaded node.
- **Architectural alignment:** More scalable than flat lists and matches real HPC physical fabrics.

### 3.3. Multi-Dimensional Load Metrics
We track **multiple resource dimensions** (CPU, memory, network bandwidth, disk I/O) rather than solely CPU utilization. We define a **composite load score** that weights each dimension based on job requirements:
- **CPU-bound jobs:** Prioritize CPU load.
- **Memory-bound jobs:** Prioritize memory load.
- **I/O-bound jobs:** Prioritize network/disk load.

This prevents bottlenecking single resource channels and reduces resource contention.

### 3.4. Learning-Augmented Load Prediction (Optional Extension)
We optionally integrate a **lightweight ML model** (e.g., Linear Regression, ARIMA, or a compact Neural Network) to **predict node load** in the near future (e.g., next 5 minutes):
- Predictions are stored within the hierarchical tree and leveraged for **proactive scheduling** (assigning jobs to nodes predicted to be underloaded).
- Extends beyond purely reactive load balancing (current load only) to predictive, proactive balancing.

### 3.5. System-Level Framework
The primary novelty is not merely the tree data structure, but the comprehensive **system-level load-balancing framework** that harmonizes:
1. Entropy-guided node grouping.
2. Hierarchical load tracking.
3. Multi-dimensional resource awareness.
4. Optional learning-augmented predictions.

*The tree acts as an enabling algorithmic component within an end-to-end framework.*

## 4. Proposed Methodology

### 4.1. System Model
- **Cluster:** $N$ compute nodes organized into $R$ racks (e.g., $N = 512$ nodes organized into $R = 16$ racks of 32 nodes each).
- **Workload:** Jobs arrive over time, each characterized by:
  - Resource requirements: CPU cores, memory capacity, network bandwidth, disk I/O.
  - Estimated runtime.
  - Job type: CPU-bound, memory-bound, or I/O-bound.
- **Load Metrics:** Per-node metrics sampled every $T$ seconds (e.g., $T = 10\text{ s}$):
  - CPU utilization (\%)
  - Memory usage (\%)
  - Network I/O (MB/s)
  - Disk I/O (MB/s)

### 4.2. Entropy Computation
For each compute node $c_i$, compute **load entropy** over a sliding window (e.g., the last 10 samples):

- **Variance-based entropy:**
  $$H_{\text{var}}(c_i) = \text{Var}(\text{CPU utilization over last 10 samples})$$

- **Shannon entropy (optional):**
  - Discretize CPU utilization into discrete bins (e.g., 0–20\%, 20–40\%, 40–60\%, 60–80\%, 80–100\%).
  - Compute Shannon entropy over the empirical probability distribution:
    $$H_{\text{Shannon}}(c_i) = -\sum_{k} p_k \log_2(p_k)$$

- **Node Classification:**
  - **Low-entropy:** $H(c_i) < \tau_{\text{low}}$ (Highly stable)
  - **Medium-entropy:** $\tau_{\text{low}} \le H(c_i) \le \tau_{\text{high}}$ (Moderate fluctuations)
  - **High-entropy:** $H(c_i) > \tau_{\text{high}}$ (Highly volatile / bursty)

### 4.3. Hierarchical Tree Structure
- **Tree Levels:**
  - **Root:** Represents the entire cluster.
  - **Level 1:** Racks (e.g., 16 rack nodes).
  - **Level 2:** Individual compute nodes (leaf nodes).
- **Node Storage Fields:**
  - Aggregated load metrics (mean CPU, memory, network, disk).
  - Load entropy (variance of CPU utilization).
  - Min/max composite load in the underlying subtree.
  - Pointers to child nodes.
- **Tree Construction:**
  1. Compute load entropy for every compute node.
  2. Group nodes into racks (physical topology or entropy-based grouping).
  3. Build tree bottom-up:
     - Leaf nodes: Individual compute nodes.
     - Internal nodes: Aggregate metrics and minimum/maximum tracking from children.

### 4.4. Job Assignment Algorithm
**On Job Arrival:**
1. **Determine job type:** CPU-bound, memory-bound, or I/O-bound (based on requested resource vectors).
2. **Compute composite load score** for each candidate node:
   $$L(c_i) = w_{\text{CPU}} \cdot \text{CPU}_i + w_{\text{mem}} \cdot \text{Mem}_i + w_{\text{net}} \cdot \text{Net}_i + w_{\text{disk}} \cdot \text{Disk}_i$$
   where weights $w$ depend on job type (e.g., for CPU-bound jobs: $w_{\text{CPU}} = 0.7$, while $w_{\text{mem}} = w_{\text{net}} = w_{\text{disk}} = 0.1$).
3. **Query hierarchical tree** to locate node with minimum $L(c_i)$:
   - Start search at the root.
   - At each internal node, traverse down to the child possessing the lower minimum-load indicator.
   - At the leaf level, retrieve corresponding compute node $c^*$.
4. **Match job to node by entropy:**
   - If the job is predictable (long-running, stable), prefer **low-entropy nodes**.
   - If the job is bursty (short, flexible deadline), allow **high-entropy nodes**.
   - If $H(c^*) > \tau_{\text{high}}$ for a predictable job, inspect adjacent branches for an alternative low-entropy node.
5. **Assign job:** Allocate job $J$ to node $c^*$.
6. **Propagate updates:** Update load metrics for $c^*$ and propagate adjusted minimums upward to the root ($O(\log N)$).

### 4.5. Periodic Rebalancing
Every $K$ minutes (e.g., $K = 5\text{ minutes}$):
1. Recompute load entropy for all compute nodes.
2. If the entropy distribution changes significantly (e.g., $>20\%$ of nodes shift entropy classification), **rebuild the tree**:
   - Re-group nodes by updated entropy classes.
   - Re-aggregate metrics bottom-up.
3. Optionally, **migrate running jobs** from overloaded nodes to underloaded nodes (if the underlying runtime system supports job migration).

### 4.6. Baselines for Comparison
- **Round-Robin (RR):** Assign jobs cyclically across nodes.
- **Least-Loaded Node (LLN):** Flat-array linear scan for the node with minimum CPU utilization ($O(N)$).
- **Work Queue:** Centralized queue dispatching jobs to the first available idle node.
- **Random:** Assign jobs uniformly at random.
- **Work Stealing:** Idle nodes actively steal jobs from overloaded nodes (if runtime supports).

## 5. Proposed Algorithms

### Algorithm 1: Hierarchical Tree Construction

```text
Algorithm 1: Hierarchical Tree Construction
------------------------------------------------------------------------
Input:  Set of compute nodes C = {c_1, ..., c_N}
        Load history for each node (e.g., last 10 CPU samples)
        Rack mapping (physical cluster topology)
Output: Hierarchical tree root node

1:  for each node c_i in C do
2:      Compute load entropy H(c_i) from recent historical samples
3:  end for
4:  Group nodes into rack subsets based on physical topology (or entropy)
5:
6:  function BuildTree(nodes):
7:      if |nodes| == 1 then
8:          return CreateLeafNode(nodes[0], metrics = c_i.metrics)
9:      end if
10:     subsets = SplitIntoSubsets(nodes)   // e.g., group by rack
11:     children = []
12:     for each subset in subsets do
13:         children.append(BuildTree(subset))
14:     end for
15:     internalNode = CreateInternalNode(children)
16:     internalNode.aggregateMetrics = Aggregate(children.metrics)
17:     internalNode.minLoad = Min(children.minLoad)
18:     return internalNode
19: end function
20:
21: root = BuildTree(C)
22: return root
```

### Algorithm 2: Job Assignment with Hierarchical Query

```text
Algorithm 2: Job Assignment with Hierarchical Query
------------------------------------------------------------------------
Input:  Hierarchical tree root
        Job J with resource requirements and job classification
Output: Selected compute node c*

1:  Determine job type (CPU-bound, memory-bound, or I/O-bound)
2:  Compute dimension weights w_CPU, w_mem, w_net, w_disk for job J
3:
4:  function QueryMinLoad(node):
5:      if node.isLeaf then
6:          return (node.computeNode, node.compositeLoad)
7:      end if
8:      // Select child with minimum subtree load
9:      bestChild = child in node.children with min(child.minLoad)
10:     return QueryMinLoad(bestChild)
11: end function
12:
13: c* = QueryMinLoad(root).computeNode
14:
15: if J.isPredictable then
16:     if H(c*) > tau_high then
17:         c* = SearchAlternativeLowEntropyNode(root, threshold = tau_high)
18:     end if
19: end if
20:
21: Assign job J to node c*
22: Update load metrics for c*
23: Propagate updated load upward to root (O(log N))
24: return c*
```

### Algorithm 3: Periodic Rebalancing

```text
Algorithm 3: Periodic Rebalancing
------------------------------------------------------------------------
Input:  Hierarchical tree root
        Entropy migration threshold tau (e.g., 20% shift)
Output: Updated tree structure

1:  shiftCount = 0
2:  for each leaf node c_i in tree do
3:      oldClass = ClassifyEntropy(c_i.H)
4:      c_i.H = RecomputeEntropy(c_i.recentSamples)
5:      newClass = ClassifyEntropy(c_i.H)
6:      if oldClass != newClass then
7:          shiftCount = shiftCount + 1
8:      end if
9:  end for
10:
11: if (shiftCount / N) > tau then
12:     root = BuildTree(C)    // Rebuild tree via Algorithm 1
13: else
14:     UpdateTreeMetrics(root) // In-place refresh of aggregated metrics
15: end if
16: return root
```

## 7. Expected Results

The evaluation should demonstrate clear empirical advantages across four key dimensions:

### 7.1. Load Imbalance
- **Load Variance:**
  - Proposed Balancer achieves **30–50% lower variance** than Round-Robin.
  - Proposed Balancer achieves **15–30% lower variance** than Least-Loaded Node (LLN).
- **Jain's Fairness Index:**
  - Proposed Balancer: **0.85 – 0.95** (values closer to 1.0 denote optimal fairness).
  - Round-Robin: **0.70 – 0.80**.

### 7.2. Job Performance
- **Average Makespan:**
  - **10–25% reduction** compared to Round-Robin.
  - **5–15% reduction** compared to LLN.
- **Average Wait Time:**
  - **15–30% reduction** compared to Round-Robin.
- **95th Percentile Wait Time (Tail Latency):**
  - **20–40% reduction** compared to Round-Robin.

### 7.3. Scheduling Overhead
- **Query Time Complexity:**
  - Proposed Balancer: $O(\log N)$ time per job.
  - LLN (flat scan): $O(N)$ time per job.
- **Empirical Execution Overhead ($N = 512$ nodes):**
  - Proposed Hierarchical Balancer: $\approx 0.1\text{ ms}$ per job dispatch.
  - LLN: $\approx 1 - 5\text{ ms}$ per job dispatch.
- **Rebalancing Overhead:**
  - Executed infrequently (e.g., every 5–10 minutes); amortization yields negligible impact on continuous throughput.

### 7.4. Scalability
- **Dispatch Time vs. Cluster Size ($N$):**
  - Proposed Balancer: Flat or logarithmic growth curve.
  - LLN: Linear growth with cluster size.
  - For $N \ge 1000$ nodes, the hierarchical balancer provides massive speedups.
